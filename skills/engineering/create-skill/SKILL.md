# 创建与完善技能

帮助用户从技能想法走到可用、符合本仓库结构的技能。采用 Claude Skill Creator 的核心迭代思路：“理解意图 → 起草 → 设计测试 → 评估 → 按反馈迭代”，但根据用户当前进度灵活加入，不要求每次从头开始。只借鉴适用于本仓库和当前环境的工作方法，不假设 Anthropic 专用脚本、viewer 或子代理在此处可用。技能草稿默认用中文，除非用户指定其他语言或仓库规范另有要求。

创建一个 `SKILL.md` 只是整个工作的一个部分。还要考虑调用元数据、生命周期分类、面向使用者的文档、索引，以及是否需要测试。

## 1. 先判断用户处于哪个阶段

先理解用户的直接请求和当前对话中已经出现的工作流。用户可能要从零创建技能、把刚完成的流程整理成技能、改进现有技能，或验证触发描述。不要对已经完成的步骤重复提问或重做。

如果当前对话已包含可复用流程，先提取其中的目标、操作顺序、使用的工具、输入和输出格式，以及用户纠正过的地方。把这些视为需求线索，而不是未经确认的规则。

## 2. 澄清意图与成功标准

只询问会实质影响技能设计的信息。先利用已有上下文；再按需了解：

- 技能要让 agent 完成什么工作？
- 何时应触发，哪些相邻请求不应触发？
- 输入、约束和预期输出是什么？
- 哪些边界情况、依赖、工具或文件格式需要支持？
- 怎样判断结果成功？
- 是否需要测试提示词或真实运行验证？

问题应短而具体。用户不熟悉技术术语时，用通俗说法解释。若信息不足且会导致不同实现，先提问再创建文件；若差异只影响次要细节，明确假设后继续。用户只要快速草稿或明确表示不需要测试时，尊重其选择。

不要把设想说成已验证事实。若缺乏真实案例，说明这是待验证的技能构想；不要虚构用户反馈或测试结果。

## 3. 检查仓库约定并规划落点

起草前阅读相关现有文件（如果存在）：

- `CLAUDE.md`、`SCOPE.md`：维护规则和项目范围。
- `.agents/invocation.md`：调用策略。
- `.agents/templates/SKILL.md`、`.agents/templates/openai.yaml`、`.agents/templates/docs.md`：文件模板。
- 目标分类的 README 和相邻技能：本地风格与职责边界。
- 顶层 `README.md`、`.claude-plugin/plugin.json`：正式技能索引和发布集合。

以本仓库规则为准，不要直接照搬其他仓库的目录、依赖或自动化。必要时可参考外部方法，但先确认当前环境实际支持所需工具。

使用简短、易辨识的 kebab-case 英文名，检查所有技能分类中是否重名。按用途和成熟度选择：

- `engineering/`：软件工程和代码库工作；正式发布并配套文档。
- `productivity/`：通用工作、学习、写作和协作；正式发布并配套文档。
- `in-progress/`：公开试验、需要反馈；默认不进入正式发布清单。
- `misc/`：仅用于符合现有冻结或非推广政策的技能。
- `deprecated/`：仅用于退役技能；尽量给出迁移或替代说明。

## 4. 设计调用方式与写作方案

选择一种调用方式，并在各目标 harness 的元数据中保持一致：

- **Model-invoked**：agent 能根据任务识别并自主调用。描述要写清技能做什么及适用场景，列出常见表达和接近边界的触发条件；避免只放抽象标题。
- **User-invoked**：用户必须主动选择或控制调用时机。Claude 兼容的 frontmatter 添加 `disable-model-invocation: true`，`agents/openai.yaml` 设置 `policy.allow_implicit_invocation: false`。对其他 harness 需核实等效配置，不能假设字段通用。

写作时优先说明为何某步骤重要，而非机械堆叠 MUST/NEVER。使用清晰的祈使句、具体的判定规则和可检查的结果。删除不必要的重复；遇到重要限制时说明原因，让 agent 能处理例外，而不是只会照抄死板规则。

对于多阶段、跨技术栈或参考材料较多的技能，保持 `SKILL.md` 聚焦于主流程和选择规则，把仅在特定分支需要的资料拆到该技能目录下的 `references/` 或 `assets/`，并明确说明何时读取。短小、聚焦的技能不必为形式拆文件。尽量让入口文件便于快速扫描；接近 500 行时优先拆分，不把行数当成硬性目标。

## 5. 起草技能及配套文件

用仓库模板创建 `skills/<分类>/<名称>/SKILL.md`。正文默认中文，保留标准字段名、命令、代码和必要的英文术语。至少写清：

- 目标和适用/不适用场景。
- 所需上下文，以及缺少输入时如何询问或安全地继续。
- 操作顺序和有意义的分支选择。
- 预期输出、验证方式、完成与停止条件。
- 安全边界，以及需要用户确认的高影响操作。

创建 `skills/<分类>/<名称>/agents/openai.yaml`，填写中文显示名和简明描述；按调用策略设置相应字段。Frontmatter 的 `name` 必须与目录名一致。描述是技能触发的关键依据，应兼顾覆盖率和准确度，既不要窄到常用场景漏触发，也不要宽到相邻任务误触发。

正式技能同时创建 `docs/<分类>/<名称>.md`，并用中文说明它做什么、何时使用、边界、所处流程和成功信号；不要把 `SKILL.md` 的步骤原样复制到介绍页。

新增或完善技能时，同步所有适用索引：

- 在 `skills/<分类>/README.md` 的正确调用方式小节添加链接。
- 在顶层 `README.md` 的正确分类与调用方式下添加链接。
- 仅对 `engineering/` 和 `productivity/`，在 `.claude-plugin/plugin.json` 的 `skills` 数组中加入 `./skills/<分类>/<名称>`。
- `in-progress/`、`misc/`、`deprecated/` 不加入正式发布清单。若技能迁移分类，清理旧索引、文档和路径。

## 6. 设计有用的测试

完成初稿后，判断测试是否能帮助用户：

- 对有客观结果的技能（如代码修改、文件转换、数据提取、固定工作流），建议先设计 2–3 个贴近真实请求的测试提示词。
- 对写作风格、审美判断等主观技能，不要强行编造自动断言；可采用用户评阅或示例对照。
- 测试应覆盖不同表达方式、重要边界和相邻但不应触发的请求，不要只写明显的成功案例。

若用户认可且仓库可保存测试，在该技能目录下创建 `evals/evals.json`，至少包含 `skill_name` 和 `evals` 数组；每项写明 `id`、真实风格的 `prompt`、`expected_output` 和 `files`。有明确、可客观核验的要求时再添加断言，不为通过率而设计简单或失真的断言。测试文件是可选项，不要仅为凑结构而添加。

先把测试案例展示给用户确认。只有在用户同意或明确要求测试时才开始运行。若可在等价环境中实际触发技能，尽量用相同任务分别测试“启用技能”和基线（无技能或旧版本），对照产物和耗时等相关信号。运行隔离、路径和权限必须符合当前环境能力；不要伪造子代理、评估器或不可用的 Anthropic 工具。

若无法实际运行技能，仍可交付测试提示词和预期结果，但要明确这是测试设计或人工推演，并非运行结果。通过静态结构检查也不等于技能效果已经验证。

## 7. 按结果迭代

读取用户对输出的具体反馈及可用的运行结果，找出背后的通用问题，不要只针对单个样例堆叠特例。留意重复出现的人工步骤是否值得做成脚本或参考文件；只有确实能减少未来重复工作时才添加。

修改时保持技能精简，解释重要规则背后的原因。尽可能保留原测试案例，避免只对已知提示词过拟合。每次迭代后重新运行相关案例；没有意义的评估工具或运行环境时，不要硬做统计。

用户对当前结果满意、反馈已解决，或改动不再带来有效改善时结束。若用户要求快速起草，可先交付草案，并把测试与后续完善作为可选下一步。

## 8. 可选：优化触发描述

技能正文稳定后，可向用户提议单独检查 frontmatter `description` 的触发准确性。若用户同意，可准备一组真实的“应触发”和“相近但不应触发”提示词，重点覆盖边界场景，并先让用户审核。只有存在真实的触发测试环境时，才报告触发率或比较结果；否则提供案例供人工检查。不要默认生成大规模测试集，也不要声称未经验证的描述已被优化。

## 9. 最终验证与汇报

在仓库根目录运行 `npm run check`，修复由本次改动造成的问题。若检查无法运行，说明原因并手动确认：

- `SKILL.md` 的 `name`、目录名和描述一致且有效。
- 调用策略在 frontmatter 和 harness 元数据中一致。
- 正式技能拥有文档页，并出现在对应索引和插件清单中。
- 非正式技能未进入正式发布清单。
- 所有引用和链接都指向正确文件；测试文件（如有）描述的是预期行为。
- 新写内容默认使用中文，除非用户或仓库规范要求其他语言。

向用户汇报新增或修改的文件、所选分类和调用方式、结构检查与实际测试结果，并明确哪些部分尚未在真实环境验证。不要把“检查通过”说成“技能已证明有效”或“兼容所有 agent”。
